# v0.1.11 additions

`lyricsWindow` scheduling sends at most 12 timestamped lines per atomic window, rather than waiting for the host to replace the visible text every two seconds. The C app advances from a monotonic playback anchor at its existing 50 ms input cadence. Media snapshots accept optional millisecond position and sample time; the Windows bridge preserves WinRT timestamp precision and album metadata. Pauses/seeks update the anchor, and track identity prevents a stale window committing onto another song. Lookup remains on demand, and both current/pending windows are freed on leaving Lyrics or media expiry. Plain lyrics retain paging. LRC offset tags are honored.

The Windows timeline interpretation follows [Microsoft's Position/LastUpdatedTime contract](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssessiontimelineproperties) and its [generated interface ordering](https://github.com/microsoft/windows-rs/blob/master/crates/libs/windows/src/Windows/Media/Control/mod.rs). Source timing can still vary by song/lyric provider; plain text cannot supply synchronized timing.

Linux collection uses one validated `stats-bundle` call for CPU, RAM, temperature and maximum-direction traffic. Values expire seven seconds after the last sample: the normal two-second interval plus five seconds of grace. Hub temperature cannot override a recently supplied PC temperature. The supervisor tolerates five seconds of status failure before stopping a collector, while explicit feature disablement stops it immediately.

Home touch and Power now open distinct Quick settings/Apps pages. Existing content page IDs remain compatible with older companions; Clock tools and Quick settings append new IDs. Weather page tests use a bounded range, so the new pages do not allocate forecast data. Charging state comes from the existing battery driver, with no invented percentage.

The optional Windows `fracture-preview.dll` compiles `device/src/preview.c`, which includes the C home renderer with all device input, socket, framebuffer and navigation code excluded. It accepts a bounded FPR1 model and selected atlas/font/notification bytes, then returns a BGRA frame to native GDI. The authenticated preview API exports the model and content-addressed in-memory drawing assets; it cannot export arbitrary device paths and never invokes `capture`. Hashes detect asset changes, while pinned TLS/bearer authentication protects transport. Private font data remains in the owner's local cache, not the release. Assets are cached by kind on disk, and the dashboard unloads its frame, C allocations and DLL when hidden. The device keeps no extra framebuffer for this feature. A one-time comparison against a device validation capture matched every pixel.

Startup uses a 1.4-second sequence at 12 frames/second, drawn procedurally into the existing framebuffer with no bitmap pack, decoder, sound or worker. A RAM marker avoids replaying on application restarts within the same boot. Bootloader/kernel images are unchanged; no full cold reboot or firmware splash replacement is claimed.

# v0.1.10 additions

The device renderer uses a bottom dock instead of adding a row per information source. A measured activity strip holds timers/stopwatch/alarm; the two-by-two metrics panel narrows when media/weather needs the right panel. Notification cards replace the dock for a configurable lifetime (10 seconds by default), with a bounded optional 48×48 RGB565 image, released on expiry/dismissal. Menu inactivity defaults to 30 seconds; active player/lyrics views remain open. All input remains independent of touch coordinates.

Weather adds a lazily allocated forecast browser. The hub requests 24 hourly records and seven daily records, bounds/checks the response, and atomically stores a compact FWE1 text cache on the device. A saved-at field avoids re-uploading unchanged data when reopening menus. The SD cache can be viewed offline with an explicit age; the array is freed when leaving Weather. This adds no HTTP or image decoder to the legacy device.

Lyrics run in a separate hub worker only while requested. Windows media snapshots retain bounded title/artist/duration state; the worker looks up LRCLIB or a supplied authenticated override, parses timestamped/plain lyrics, and sends only the three displayed lines. The PC cache is bounded to eight entries. Track identity checks reject stale updates. Multiple display commands now share a validated Telnet batch, reducing connection churn during notifications/media/lyric updates.

PawnIO authorization elevates only a signed-module temperature helper through ShellExecuteEx/runas after an explicit app action. The regular worker owns a temporary loopback receiver protected by a random token. The privileged helper receives a module-directory path and that endpoint/token, not hub credentials; module contents must match pinned hashes, and the only hardware requests are the fixed temperature reads. Idle hardware handles are released; the helper exits when its receiver closes or after the idle grace period. Actual UAC/sensor acceptance is pending on the owner's Windows PC.

Windows app updates select a newer numeric release tag, bound downloads, verify the named asset's SHA-256, stage a distinct updater executable, close the old installation, run its Inno installer and reopen dashboard/tray. Settings are retained; no update check runs unless requested. The Linux web action uses the versioned per-user installer. FractureOS application updates do not automatically activate a device payload. Authenticode signing and signed release manifests remain future work.

The vector FractureOS mark is the source for shared ICO/PNG/SVG exports. The executable, tray, window, Inno installer and webpage use that mark. Windows resources are built with pinned go-winres v0.3.3, a build-only dependency; the app continues using the Go standard library. Device deployment prepares a backup/replacement of the TomTom volume icon. That replacement and final activation await reconnection.

# v0.1.9 additions

The Windows dashboard is a separate Go/Win32/GDI process with native controls, rounded owner-drawn buttons and a timer that polls only its visible Dashboard tab. It closes completely when dismissed; the tray supervises optional media/temperature workers. The independent web dashboard uses the same command/status and integration configuration endpoints. Neither frontend adds a browser runtime to the executable.

The Linux weather supervisor launches a separate worker only when the provider is enabled and a clock with weather enabled is visible. The worker fetches bounded HTTPS JSON, checks numeric ranges/freshness and caches a small summary for 15 minutes. It refreshes the device lease every 30 seconds; values expire after 30 minutes. Weather-disabled requests cannot refresh the hub's device summary. Forecast logic and TLS do not run on the TomTom.

Device settings now persist feature switches and appearance. Crowded faces use transient horizontal geometry without overwriting the selected face layout. Date text centers independently of digit scaling. Status content is capped at five rows, with missing metrics removed and one maximum-direction traffic value. CPU temperature replaces the disk widget. Clock/menu code remains monolithic; this is bounded/lazy data and process loading, not a completed dynamic C module loader.

The neon preset reuses the existing Nunito atlas. Connection uses a 15-second heartbeat and a chain icon. Charging state is read from the actual battery ioctl only when the neon face is drawn, at most once every 30 seconds; voltage is not converted into a made-up percentage. Day mode currently uses a shared high-contrast palette across faces, and automatic mode follows configured local 07:00–19:00.

Notifications use a bounded authenticated POST endpoint, exact case-insensitive app exclusions and a two-second delivery limit. Direct Windows toast capture and notification sounds are not implemented. Microsoft requires a [User Notification Listener capability and user consent](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/notification-listener); Inno installation alone does not supply that package capability.

Windows temperature support uses PawnIO's documented [device IO-control contract](https://github.com/namazso/PawnIO/blob/master/PawnIO/include/pawnio_um.h) with official signed [IntelMSR / AMDFamily17 modules](https://github.com/namazso/PawnIO.Modules/releases/tag/0.2.11). No DLL is bundled. The module archive is opt-in and SHA-256 pinned; the driver verifies modules. Intel reads target/thermal status registers; AMD uses the shared Global\Access_PCI mutex for its indexed SMN temperature register. No temperature-control/MSR-write function is requested. Conversion and older Ryzen offsets follow the hardware conventions also documented in [LibreHardwareMonitor](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/blob/master/LibreHardwareMonitorLib/Hardware/Cpu/Amd17Cpu.cs). Only Windows x64 is supported by this temperature path; real hardware validation is pending. While actively shared, PC temperature takes precedence over hub temperature and carries a PC label; other resource widgets continue to describe the hub.

The Inno installer ships only the native app, Start-menu links and its uninstaller, with optional login startup. It installs per-user and keeps configuration on uninstall. The PowerShell bootstrap detects x64/ARM64, verifies SHA-256 and launches the matching setup executable. Signed release manifests and Authenticode signing of FractureOS itself remain future work.

# v0.1.8 additions

The C app now uses small header modules for page navigation, read-only button sampling/power actions, and bounded media/status state. CPU/RAM symbols, filesystem usage and default-route network rates share the optional Linux collector. The Windows media worker uses native WinRT COM interfaces on a dedicated MTA thread and Windows Core Audio output-volume stepping. It posts updates to `/api/media` through the same pinned TLS/bearer channel; no Spotify developer API remains. Artwork is a fixed 96×96 RGB565 buffer allocated only on the player screen and freed when leaving it. Media becomes stale after 20 seconds and actions expire after 10 seconds. The Windows tray checks enabled demand every three seconds; active media polling is every two seconds. Disabled sharing makes no media API calls and launches no worker.

The live button indicator uses a read-only GPIO page mapping only after matching model 19 (Casablanca) and CPU 4 (S3C2412). GPF0 input is active low, at physical 0x56000054; its configuration must be input/EINT. No GPIO register is written. Other hardware falls back to completed-release ioctl durations without a live indicator. SDK sources: `tomtomgo-iocasablanca-*.h`, `tomtomgo-type.c`, `regs-gpio.h`. Suspend writes `mem` to `/sys/power/state`; restart/shutdown use the kernel reboot API. These power actions were not executed during validation.

Windows media ABI reference: [Microsoft Windows SDK generated bindings](https://github.com/microsoft/windows-rs/tree/master/crates/libs/windows/src/Windows/Media/Control), [media-session usage](https://devblogs.microsoft.com/oldnewthing/20231108-00/?p=108980), [Core Audio endpoint volume](https://learn.microsoft.com/en-us/windows/win32/api/endpointvolume/nn-endpointvolume-iaudioendpointvolume). The four Windows vet unsafe-pointer diagnostics occur at foreign COM vtable/HSTRING/buffer addresses. Their ownership and bounds were reviewed; cross-compilation cannot establish runtime ABI correctness. A real Windows check remains required.

# v0.1.7 implementation

This describes the code that exists. ARCHITECTURE.md and MODULES.md describe the broader target design; their full registry, wire protocol, face composition model and signed updater are not implemented yet.

## Device

`device/src/fracture.c` owns `/dev/fb`, touchscreen events, the Barcelona button-duration snapshot ioctl and PWM brightness. It takes a process lock, exposes a root-only Unix control socket and copies the small framebuffer only when an actual redraw is needed, without retaining a second shadow framebuffer. `faces.h` parses bounded data-only face files and loads one alpha atlas. The old Nano-X application and information sidebar are not dependencies. The selected face, profile, theme, brightness, UTC offset and visual alarm settings are saved through temporary files and rename. FAT durability across sudden power loss is not guaranteed by this mechanism.

The minimal face redraws on minute changes or input/configuration. Visible seconds, a blinking colon, timers, stopwatch and desk view update once per second. Menu selection transitions run for 180 ms at the existing polling cadence, then stop. A 45.7 KB UI text atlas supplies antialiased mixed-case text without a font engine. A 50 ms poll remains necessary for the custom power-button snapshot driver; this is not interrupt-only idle behavior. Clock/menu/timer functionality is currently compiled together, while the large atlas is allocated only when selected. Optional integrations are absent from this release rather than dormant background services.

Power uses the kernel's non-destructive button-event snapshot rather than stealing the shared hardware status flag. The touch handler uses BTN_TOUCH and pressure only, debounces very short contacts, and recognizes single/double/held presses. Physical long-press power policy and a noisy cracked panel still require user hardware acceptance.

`boot.sh` stays in the foreground because the existing `/etc/rc` forces a reboot if its application chain returns. Repeated short-lived failures return to the preserved OpenTom startup. During live replacement, old foreground startup shells are stopped, not killed, to keep that init chain alive. These small stopped processes and unreaped old children remain until a planned reboot; no reboot was performed. The new startup entry is installed for next boot.

## Host

Go standard-library code serves an authenticated, pinned-TLS API, serializes commands to the device and briefly caches status. For this first release, the final hop uses the existing root Telnet connection on the trusted USB link. The C/Go framed HMAC protocol described in the design is future work. Do not expose root Telnet or this early hub directly to the Internet; use the owner's private network for remote access.

Linux resource collection runs as a separate child process only when `hub_metrics` is enabled and the Desk screen is visible. The process is cancelled and reaped when its consumer disappears. Windows collection is not implemented. The tray blocks on the native Windows message loop; it does not run polling collectors. Settings launch as another process serving a session-protected localhost page and opening the user's browser; the settings process expires after five idle minutes. This is not the originally proposed fully native Studio or a drag-and-drop widget editor.

## Installation and updates

Linux installation is per-user, with a versioned host release directory, launcher and optional systemd user service. Windows uses a PowerShell/WinForms installation window, per-user files, a Start menu shortcut and HKCU uninstall registration. Windows installation does not change machine-wide execution policy; its uninstaller uses a process-scoped policy option. No Windows drivers or elevated install are needed for these features.

Downloads use HTTPS and release checksums. Device uploads are staged via a temporary, tokenized HTTP endpoint on the USB host, then read back and SHA-256 verified. The installer preserves startup and firmware files as private host backups; it does not write firmware. New binaries occupy a new release directory. Activation is health-checked; a failure after replacing startup attempts restoration. These checks are not a signed update chain, A/B firmware system, complete activation journal or interrupted-power guarantee. Retrying a partially staged release may require inspecting the abandoned slot; it will never overwrite mismatched same-version executables.
